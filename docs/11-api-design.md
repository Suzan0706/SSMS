# 11. API Design

## 11.1 Conventions

| Topic | Convention |
|---|---|
| Base URL | `https://<school-domain>/api/v1` (major version in the path; additive changes only within v1) |
| Docs | Swagger UI at `/docs`, OpenAPI JSON at `/api/v1/openapi.json` (generated by FastAPI) |
| Auth | `Authorization: Bearer <access JWT>`; `POST /auth/login` uses an OAuth2 password form, so the Swagger "Authorize" button works |
| Format | JSON in UTF-8; money as decimal strings in TZS (`"680000.00"`); dates `YYYY-MM-DD`; times `HH:MM`; timestamps ISO 8601 with offset |
| Phones | Accepted as `0754 000 001`, `+255 754 000 001` or `255754000001`; always returned as `255754000001` |
| Paging | `?page=1&size=25` → `{items, total, page, size}`; `size` ≤ 100 |
| Errors | `{"detail": {"code", "message_en", "message_sw", ...extra}}`; validation errors use FastAPI's standard 422 body |
| Tracing | Every response carries `X-Request-ID`, the same id that is stored in `audit_logs.request_id` |

**Status codes:**

| Code | Meaning |
|---|---|
| 200 | OK |
| 201 | Created |
| 202 | Accepted (background job) |
| 204 | No content |
| 401 | Not logged in, or bad credentials |
| 403 | Logged in but the role is not allowed |
| 404 | Not found, or not yours (no information leak) |
| 409 | Conflict: duplicate, clash, wrong state, ledger rule |
| 422 | Validation or business-rule failure |
| 423 | Account locked |

**Database errors are mapped to these codes.** `23505` → 409 DUPLICATE, `23P01` → 409 CLASH, `23503` → 409 INVALID_REFERENCE, `23514` → 422 CHECK_FAILED, `P0001` → 409 RULE_VIOLATION. See [backend/app/core/errors.py](../backend/app/core/errors.py).

**Role abbreviations:** ADM Admin · REG Registrar · BUR Bursar · INS Instructor · STU Student · PAR Parent · *any* = any logged-in user. ✅ marks endpoints in the tested reference implementation ([backend/](../backend/)). The other rows are the design for the remaining modules.

## 11.5 Running the API locally

```bash
cd backend
python -m venv .venv && . .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
cp .env.example .env                                  # then edit SMS_DATABASE_URL and SMS_JWT_SECRET
createdb sms && alembic upgrade head                  # runs db/schema.sql
psql -d sms -f ../db/seed.sql                         # optional sample school
uvicorn app.main:app --reload                         # http://localhost:8000/docs
celery -A app.tasks.celery_app worker --loglevel=INFO # second terminal (needs Redis)
```

## 11.7 Migrations

- `alembic upgrade head` applies [0001_baseline](../backend/alembic/versions/0001_baseline.py), which executes `db/schema.sql`. The schema contains EXCLUDE constraints, a range type, triggers and views that autogenerate cannot express, so the hand-written DDL is the baseline.
- Later changes: edit the models, run `alembic revision --autogenerate -m "..."`, review the script, and add raw SQL (`op.execute`) for triggers or views.
- `alembic check` runs in CI. It ignores database objects the ORM does not map, and treats enums stored as `VARCHAR + CHECK` as matching. It currently reports **no differences** between the models and the migrated schema.
